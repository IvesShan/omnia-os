# Omnia 工具调用问题全面分析报告

## 一、问题现象

用户反馈 Omnia 经常不调用工具，即使系统提示中明确要求"必须先调用工具再回答"。

## 二、根本原因分析

### 🔴 核心问题：多层防御机制存在漏洞

Omnia 有三层工具调用机制，但每一层都有缺陷：

---

### 第 1 层：系统提示中的"硬规矩"（wake.py）

**位置**: `src/omnia/wake.py` 第 141-155 行

```python
### 🔴 硬规矩：必须先调用工具再回答

**任何需要读取文件、查询状态、验证结果的场景，都必须先调用工具再回答。** 
典型场景包括（不仅限于）：
- 用户说"检查""确认""验证""查看""读文件""看看效果""分析""重新分析"
- 用户问"有没有生效""改好了吗""提交了吗""检查一下""怎么样了""状态"
- 用户说"调用工具""用工具查""跑一下"
- 涉及查询文件内容、Git 状态、服务运行状态、代码分析

违规后果：如果未调用工具就直接声称"已完成""已修改"，一律视为错误。
```

**问题**：
1. ❌ **这只是文本指令，LLM 可能忽略** - 没有强制机制
2. ❌ **没有示例** - LLM 不知道具体如何调用
3. ❌ **没有负面反馈** - LLM 违规后没有惩罚

---

### 第 2 层：前置工具检查钩子（tool_preroll.py）

**位置**: `src/omnia/tool_preroll.py`

**机制**：在消息发给 LLM 之前，检查是否命中关键词，如果命中则直接执行 shell 命令并注入结果。

```python
def check_and_run(user_message: str) -> str:
    """检查用户消息是否命中关键词触发器。如果命中，执行对应的 shell 命令并返回结果文本。"""
    results = []
    for pattern, commands in TRIGGER_RULES:
        if re.search(pattern, user_message, re.IGNORECASE):
            results.append(f"🔍 [前置工具检查] 命中关键词: '{pattern}'")
            for desc, cmd in commands:
                result = subprocess.run(cmd, shell=True, ...)
```

**问题**：
1. ❌ **这是"绕过"方案，不是"引导"方案** - LLM 没有学习如何调用工具
2. ❌ **关键词覆盖不全** - 只定义了 7 种场景
3. ❌ **注入的结果可能被忽略** - LLM 可能不基于注入的结果回答
4. ❌ **破坏了工具调用的标准流程** - 工具结果不在对话历史中

---

### 第 3 层：should_require_tool() 函数（chat_handler.py）

**位置**: `src/omnia/chat_handler.py` 第 12-38 行

```python
def should_require_tool(user_message: str) -> str | None:
    """
    智能判断是否应该强制调用工具。
    
    注意：DeepSeek reasoning 模型不支持 tool_choice: "required"，
    所以统一返回 "auto" 让模型自行决定。
    """
    trigger_keywords = [
        "检查", "确认", "验证", "查看", "读取", "读文件",
        "改好了吗", "生效了吗", "有没有", "状态",
        ...
    ]
    
    for kw in trigger_keywords:
        if kw in user_lower:
            return "auto"  # ❌ 问题：只返回 "auto"，不强制
    
    return None
```

**问题**：
1. ❌ **只返回 "auto"，不强制** - LLM 可以自己决定不调用工具
2. ❌ **DeepSeek 限制** - 注释说 DeepSeek 不支持 `tool_choice: "required"`
3. ❌ **关键词列表有限** - 无法覆盖所有场景

---

### 第 4 层：工具调用逻辑（chat_handler.py）

**位置**: `src/omnia/chat_handler.py` 第 195-215 行

```python
# 调用模型
use_tools = tools_schema if not tool_calls_executed else None  # ❌ 问题：工具执行后不再传递工具

# 智能判断 tool_choice（不传 None 即为 API 默认行为）
tool_choice = should_require_tool(message) if use_tools else None
if tool_choice:
    print(f"[Chat] Tool choice: {tool_choice}")

```

**问题**：
1. ❌ **工具执行后禁用工具** - `use_tools = tools_schema if not tool_calls_executed else None`
   - 这意味着如果第一轮没有调用工具，后续也不会调用
2. ❌ **tool_choice 可能是 None** - 如果 `should_require_tool()` 返回 None，则不传 tool_choice

2. ❌ **明确要求"不要输出工具调用格式"** - 这会阻止后续工具调用

## 三、问题链条

```
用户说"检查一下"
    ↓
tool_preroll.py 命中关键词
    ↓
执行 shell 命令，注入结果到系统提示
    ↓
LLM 收到消息时已经包含了工具结果
    ↓
LLM 可能：
  1. 基于注入的结果回答（好）
  2. 忽略注入的结果，自己编造（坏）
  3. 尝试调用工具（但 tool_choice="auto" 不强制）
    ↓
如果 LLM 选择不调用工具：
    ↓
should_require_tool() 返回 "auto"（不强制）
    ↓
LLM 直接回答，不调用工具
    ↓
问题出现！
```

## 四、深层原因

### 1. **设计哲学问题：绕过 vs 引导**

`tool_preroll.py` 的设计哲学是"绕过 LLM 的工具调用"，而不是"引导 LLM 调用工具"。

这导致：
- LLM 没有学习如何正确调用工具
- LLM 习惯了"别人帮我执行工具"的模式
- 当 `tool_preroll.py` 没有命中关键词时，LLM 就不会调用工具

### 2. **API 限制问题：DeepSeek 不支持 tool_choice: "required"**

代码注释明确说：
```python
# 注意：DeepSeek reasoning 模型不支持 tool_choice: "required"，
# 所以统一返回 "auto" 让模型自行决定。
```

这意味着：
- 无法强制 LLM 调用工具
- 只能"建议" LLM 调用工具
- LLM 可以选择不调用

### 3. **关键词覆盖不全**

`TRIGGER_RULES` 只定义了 7 种场景：
1. 进度条/上下文占比
2. 消息上限/聊天卡顿
3. Three.js/神经图谱暂停
4. Git 状态/提交记录
5. 服务/进程/端口检查
6. 文件读取/查看代码
7. 通用"检查/分析"动词

但实际上有很多场景需要工具调用，例如：
- 修改文件后验证
- 部署后检查
- 测试运行结果
- 日志分析
- 配置验证
- ...

### 4. **系统提示不够强**

虽然系统提示中有"🔴 硬规矩"，但：
- 没有具体示例
- 没有负面反馈
- 没有强制机制

LLM 可能会认为这只是"建议"，而不是"强制要求"。

## 五、解决方案建议

### 方案 A：强化系统提示（短期）

在系统提示中添加：
1. **具体示例** - 展示正确和错误的工具调用方式
2. **负面反馈示例** - 展示违规后果
3. **Few-shot 学习** - 提供几个正确调用工具的对话示例

### 方案 B：改进 tool_preroll.py（中期）

1. **扩展关键词覆盖** - 添加更多场景
2. **改进注入方式** - 将工具结果作为"tool"角色消息，而不是注入到系统提示
3. **添加强制标记** - 在注入结果后添加"必须基于此结果回答"的指令

### 方案 C：改进 should_require_tool()（中期）

1. **支持多 provider** - 对于支持 `tool_choice: "required"` 的 provider，强制调用
2. **改进关键词匹配** - 使用语义相似度而不是精确匹配
3. **添加上下文感知** - 根据对话历史判断是否需要工具

### 方案 D：改进工具调用逻辑（长期）

1. **移除"工具执行后禁用工具"的逻辑** - 允许多轮工具调用
2. **改进消息重建策略** - 保留关键历史
3. **添加工具调用验证** - 检查 LLM 是否正确调用了工具

### 方案 E：添加后验证机制（长期）

1. **检查回答是否基于工具结果** - 如果工具结果已注入，检查回答是否引用
2. **添加自动重试** - 如果检测到 LLM 忽略工具结果，自动重试
3. **记录违规行为** - 统计 LLM 违规次数，用于改进系统提示

## 八、总结

Omnia 不调用工具的根本原因是：

1. **系统提示不够强** - 只是文本指令，没有强制机制
2. **tool_preroll.py 是绕过方案** - LLM 没有学习如何调用工具
3. **should_require_tool() 不强制** - 只返回 "auto"，LLM 可以选择不调用
4. **工具调用逻辑有缺陷** - 工具执行后禁用工具
5. **API 限制** - DeepSeek 不支持 tool_choice: "required"

要解决这个问题，需要：
1. 强化系统提示，添加示例和负面反馈
2. 改进 should_require_tool()，对支持的 provider 强制调用
3. 移除"工具执行后禁用工具"的逻辑
4. 扩展 tool_preroll.py 的关键词覆盖
5. 添加后验证机制
